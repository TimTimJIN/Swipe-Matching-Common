## 要件

### 確定事項と仮定

- ユーザー要望：iPhoneとAndroidで動くスワイプマッチングシステムを共通コードで開発。FlutterまたはReact Nativeを用い、必要に応じSwift／Kotlinを併用する。
- 追加回答：恋愛限定ではなく「用途横断の共通基盤」を優先する。
- 対象利用者：基盤を使うサービス運営者と、そのサービスの会員。公開対象業界・国・年齢層は未決定。
- 解決する課題：サービスごとに会員管理・カード表示・成立処理・会話・通報を作り直す負担を減らす。
- 今回の範囲：調査、設計案、実装バックログ、検証計画、開発環境とレビュー接続の確認。契約・購入・公開・本番リソース作成は行っていない。
- コード共通化率は未測定。100%共有や固定の削減率は約束しない。ビルド・署名・OS権限・ストア申請はOSごとに必要。

### 共通化の3層

| 層 | 共通にするもの | 差し替えるもの |
| --- | --- | --- |
| OS間 | 画面、入力検証、状態管理、APIクライアント、ドメインモデル | OS権限、署名、SDK連携、ストア課金などのアダプター |
| サービス間 | 認証、候補取得、意思表示、成立状態、会話、通報、監査 | プロフィール項目、候補条件、成立ルール、会話開始権限、文言・テーマ |
| 運営・配置 | API契約、DBマイグレーション、管理機能、CI手順 | サービスID、運営権限、データ保持、地域、配布・インフラの分離 |

共通コードの再利用と、複数顧客を同一DBで運営するマルチテナント化は別の判断とする。初期は単一サービスの配置で動かしつつ、サービス境界をモデルに持たせる。複数サービスのデータを同一DBへ収容する前には隔離試験を必須とする。

### 最初に通す操作と範囲

登録→プロフィール入力→候補カード閲覧→興味あり／見送り→相互意思確認で成立→テキスト会話→通報／ブロック→退会。

技術検証では架空の2設定「趣味仲間（人対人）」と「仕事相談（人対案件）」を用意し、共通部分を変更せずに切り替えられるかを確認する。これらは実サービスの選定ではなく検証データである。

| 段階 | 対象 | 対象外 |
| --- | --- | --- |
| 技術検証 | カード操作、設定切替、両OSビルド、架空データで成立と会話 | 公開、決済、実ユーザー、AI推薦 |
| 最小実用版 | 認証、画像、候補絞り込み、相互成立、会話、通知、通報管理、削除 | 動画通話、複雑なランキング、汎用ノーコードビルダー |
| 次段階 | 非対称の応募／承認、課金、本人確認、複数運営者、監査強化 | 業界未確定の機能の先行実装 |

人対案件の正式運用には応募者・案件オーナー・代理承認者の権限を定義する。人対人を前提にした user_a／user_b だけの設計にはしない。

## 設計と実装

### 技術選定の暫定結論

第一候補は Flutter。独自カードUIと複数用途の画面を統一することを重視した設計判断であり、性能比較の実測結果ではない。TypeScript／Reactの既存資産・担当者がいる場合、またはWindowsからのクラウドビルド運用を優先する場合は React Native＋Expo を有力候補とする。両方の本番実装を並行保守しない。

| 観点 | Flutter | React Native＋Expo |
| --- | --- | --- |
| 主言語 | Dart | TypeScript／JavaScript |
| UI | Flutterのウィジェットで共通構築 | React Nativeのコンポーネントで共通構築 |
| スワイプ | ジェスチャーとアニメーションで実装。実機計測が必要 | ジェスチャー／アニメーションライブラリを評価し実装。実機計測が必要 |
| OS固有コード | プラグイン、Platform Channels、PigeonでSwift／Kotlinと接続 [S1] | Expo Modules APIでSwift／Kotlinと接続。独自ネイティブコードはdevelopment buildで確認 [S3][S4] |
| Windows中心の開発 | Android開発可能。iOSローカルビルドはmacOS／Xcodeが必要 [S2] | Android開発＋ExpoのクラウドiOSビルドが候補。iOSローカル検証にはMac／Xcodeが必要 [S4][S5] |
| Web管理画面との共有 | データ契約は共有可能。Webを別言語にする場合は生成などが必要 | TypeScriptの型・検証ロジックを共有しやすい。DOMの画面はそのまま共有できるとは限らない |
| 選定条件 | モバイルUI統一を優先し、Dart採用が可能 | React人材・資産、TypeScript統一、Expo運用を優先 |

採用ゲート：同一のカード仕様で選定候補の両OS実機確認、画像表示、画面遷移、通知、必要な外部SDKの適合性を確認する。問題がなければ固定。問題がある場合に限り他候補で最小比較する。SDKの版は着手時にstable／互換組合せを確認し、ロックファイルとCIに固定する。

### OS固有実装の境界

| 機能 | 通常の方針 | Swift／Kotlinを追加する条件 |
| --- | --- | --- |
| カード、フォーム、会話画面 | 共通UI | 計測で特定OSの問題が残り、共通側の修正で解決しない |
| カメラ、写真、位置情報、通知、認証 | 保守されている対応プラグインを優先 | SDK未対応、OS固有機能、拡張、必要な挙動が提供されない |
| 本人確認・外部SDK | 対応プラグインを評価 | ベンダー提供がネイティブSDKのみ |
| 決済 | OSの購入・復元をアダプター化 | 採用ライブラリで対象要件が満たせない |

新しいネイティブ層は型付きの小さい境界に閉じ込め、共通側から直接OS判定を散在させない。既存プラグイン利用でもOSごとの権限設定・実機試験は省略しない。

### 論理構成案

モバイルアプリ → 認証済みAPI／サーバー側成立処理 → PostgreSQL。
画像は非公開オブジェクトストレージと期限付きURL。会話更新は認証付きリアルタイム購読、通知はサーバーのイベント処理から配信。運営画面は別の管理権限でAPIへ接続する。

- バックエンド暫定候補：Supabase／PostgreSQL。関係・一意性・取引をDBで表しやすいことを重視する。公開スキーマにはRLSを適用し、管理キーをアプリへ配布しない [S8]。
- 代替：Firebase Auth／Firestore／Functions。Firestoreにもトランザクションがあり [S9]、排除しない。関係検索・重複排除・運営集計の設計負担、利用量に応じた費用を比べて決める。
- 配置先や価格プランは未選定。国内保管、復旧要件、運用担当、既存クラウド契約が決まれば再評価する。
- サーバーに成立判定を集約し、モバイルの判定だけでは成立させない。外部サービス切替は認証・保存・通知等の境界で吸収する。

### データ・成立処理

| エンティティ | 役割と制約案 |
| --- | --- |
| Service／Membership | サービス設定、参加者、役割。サービスを跨いだ閲覧を拒否 |
| Actor／Subject | 操作主体と表示対象を分離。対象は人・案件など。所有者・操作権限を明示 |
| Profile／Media | 公開項目と非公開情報を分離。項目スキーマと版を管理 |
| Interaction | 興味あり／見送り。サービス・主体・対象で重複管理。再送キー必須 |
| Match／MatchParty | 成立状態と当事者・対象・ルール版。サービス内の正規化された組に一意制約 |
| Conversation／Message | 成立と参加権限に紐付く。送信IDで再送重複を防止 |
| Block／Report | 即時遮断と運営審査。通報者情報を相手へ公開しない |
| Outbox／Audit | DB更新後の通知イベント、操作監査。個人情報のログ流出を防ぐ |

相互意思確認：認証・所属・対象権限・ブロックを確認→組単位の直列化／適切なロックで意思表示を保存→逆向き意思を読み取り→一意なMatchを作成→同一取引で通知イベントを保存。単に双方が逆向き行を読んでINSERTするだけでは、同時操作時に成立を取りこぼす可能性がある。並行操作試験を必須とする。

通知はat-least-onceを前提に冪等処理し、プッシュの厳密な1回配送を保証しない。アプリ内の成立・会話データが正本。人対案件では「案件への応募」と「応募者への承認」を別の意図として定義する。

ブロック／退会とメッセージ送信が競合しても、サーバー側で最新権限を評価する。画像URLの失効期限、購読解除、端末キャッシュの破棄も設計する。正確な位置座標は相手へ渡さず、必要な場合のみ概略地域を表示する。

### 画面・導線・エラー復帰

1. 登録・ログイン：利用目的と同意を提示。入力エラーを該当項目に表示し、修正済みの値を保持。
2. プロフィール：公開範囲を明示。画像アップロード失敗時は再試行・削除が可能。
3. 候補：カード詳細、興味あり／見送りボタン。候補なし、読込中、通信失敗を区別。
4. 成立一覧・会話：送信中／失敗／再送を区別。サーバー確認前に成立確定と表示しない。
5. 安全・設定：通報、ブロック、通知設定、アカウント削除。
6. 運営：通報一覧、審査・停止・監査。管理者権限は一般会員と分離。

スワイプはボタンでも代替可能にする。VoiceOver／TalkBackのラベル・読み上げ順、文字拡大、色以外の状態表示、Reduce Motion、キーボード／スイッチ操作、フォーカス移動を確認する。通信断では未送信を明示し、再送で重複成立させない。

### 配布・ストア対応

- Appleは同等アプリの重複、テンプレート由来アプリの提出方法、既存恋愛アプリとの差別化を審査する。コード共有自体と審査通過は別問題 [S6]。
- Google Playにも反復コンテンツの制約がある [S7]。初回は1つの用途で価値を実証し、単一アプリ内の切替か独立ブランド配布かは事業上の差と審査要件で決める。
- 投稿画像・プロフィール・会話を扱うため、フィルタ、通報、ブロック、運営への連絡導線を初期から扱う [S6]。対応者・対応期限・記録方法も公開前に決める。
- アカウント削除はアプリ内から開始できる導線を設ける。Google Play用には外部の削除申請ページも用意する [S7][S10]。
- 恋愛・人材・未成年向けなどの各用途では、地域の制度、本人確認、年齢、課金・プライバシーの追加確認が必要。用途未定のため法的適合を判定していない。対象用途の確定後に公式資料で別途確認する。
