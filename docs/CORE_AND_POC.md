# 共通コア・技術検証仕様 v0.1

状態：設計案。実装・実機検証・独立レビュー未実施。

## 境界

| モジュール | 入力 | 出力・責任 |
| --- | --- | --- |
| ServiceConfig | 用途ID、設定版、項目スキーマ、テーマ、ルールID | 登録済みルールと許可済み項目を参照。任意コードは実行しない |
| CandidateQuery | 認証主体、サービスID、フィルター、カーソル | 表示可能な対象だけ返す。ブロック・停止・退会を除外 |
| InteractionCommand | 主体、対象、意図、再送キー、設定版 | サーバーで認可・整合性を確認。再送は同じ結果 |
| MatchPolicy | 意思表示と対象所有者・参加権限 | 成立の可否と当事者。クライアントは成立を確定しない |
| ConversationPolicy | 成立ID、参加者、最新の制限状態 | 読取・送信・購読を都度認可 |
| PlatformAdapter | 写真・通知等の型付き要求 | OSごとの許可・取消・失敗を共通の結果へ変換 |

例外は validation_error / forbidden / stale_config / conflict / temporarily_unavailable を区別する。未送信・送信結果不明・確定済みをUIで区別し、結果不明時は同じ再送キーで照会・再送する。

## 2用途の検証設定

| 項目 | 趣味仲間 | 仕事相談 |
| --- | --- | --- |
| 対象 | 人 | 案件 |
| 入力項目 | 趣味、地域、紹介文 | 分野、相談内容、稼働条件 |
| 意思表示 | 興味あり／見送り | 応募／見送り |
| 成立条件 | 当事者同士の興味あり | 応募＋案件所有者の承認 |
| 会話参加者 | 両会員 | 応募者と案件所有者 |

初回は各設定20件の架空データを使用する。表示設定の切替だけでは利用者のサービス所属・認可は変更しない。人対案件では第三者の承認を拒否する。

## PoCの作業順

1. 共通インターフェースと架空データを作る。最初はバックエンドアダプターを模擬実装し、模擬であることを明示。
2. カード詳細→ボタン／スワイプ→意思表示状態を作る。通信失敗・候補なしの画面も用意。
3. 2用途の設定を切り替え、共通コアを変更せず表示・操作を変えられるか確認。
4. サーバー処理を接続し、同時送信・再送・ブロック競合を検証。模擬実装の合格を実DBの合格へ流用しない。
5. iPhone／Android実機で操作・性能・通知・権限拒否・アクセシビリティを検証。

## 先に確認するテスト

- 相互いいねの同時実行で成立を取りこぼさず、成立レコードが1件だけになる。
- 再送キーの同じ要求は重複処理せず、同じキーに異なる本文なら拒否する。
- 別サービスの対象・会話・画像にアクセスできない。
- ブロックと送信の競合ではDB上の順序を定義し、ブロック確定後の送信を拒否する。
- 案件所有者以外による承認を拒否する。
- 設定版が古い場合は入力を保持して更新を促す。
- スワイプせずボタンと読み上げだけで主要操作を完了できる。
